# PMIRI technology decisions

This file records implementation choices outside the immutable documentation
archive. Each choice is behind a replaceable boundary and does not widen the
authority granted by the archive.

| ID | Decision | Current implementation | Status / replacement point |
|---|---|---|---|
| TD-001 | Keep JSON/blob as the compatibility backend and add SQLite as the transactional production-oriented adapter. | `pmiri.store.LocalStore` retains atomic replace/`fsync`/writer-lock behavior; `pmiri.store.SQLiteStore` uses WAL, `synchronous=FULL`, busy-timeout transactions, content-addressed blobs, `migrate_from_local_store`, `backup_to` and safe no-overwrite `restore_from_backup`. | Implemented and locally tested for history-preserving migration, concurrent writers, corruption detection, read-only access, verified snapshot backup and fingerprint-verified restore; final deployment, encryption and operational migration approval remain open. |
| TD-002 | S0 retrieval is deterministic lexical retrieval. | `pmiri.retrieval.Retriever` with project scoping and stable ordering. | Implemented for S0; embeddings/reranking remain a separate decision. |
| TD-003 | Provider and connector calls cross an explicit transport seam. | Exact Gate-D fence plus in-memory deterministic doubles. | Implemented for local evidence; real transport requires an explicit authority/deployment decision. |
| TD-004 | Network evaluation consumes supplied DNS/TLS observations and never performs I/O by default. | `pmiri.network`, `pmiri.policy`, `GateDDecisionEngine`. | Implemented fail-closed; DNS/TLS/socket implementation remains outside the current authorization. |
| TD-005 | Gate-D records are validated through one standards-complete registry boundary. | `pmiri.schema.SchemaRegistry` defaults to `jsonschema` Draft 2020-12 with a `referencing` PMIRI URI registry; `backend="subset"` is explicit compatibility only. | Implemented and exercised by runtime/tests; dependency supply-chain pinning, update review and production deployment validation remain. |
| TD-006 | Clean-room readiness is evidence, not a local boolean. | `pmiri.attestation.load_attestation`, `pmiri.clean_room`, `pmiri.controlled_replay`. | Implemented fail-closed; OS isolation and independent observation must come from the controlled environment. |
| TD-007 | R-FC status is preserved per case and cannot be promoted by the runner. | Schema-shaped `BLOCKED` evidence records from `rfc-status`; PASS requires executed replay and independent review. | Implemented as evidence inventory; replay remains blocked. |
| TD-008 | Artifact sealing distinguishes byte integrity from completeness. | Role-aware canonical manifest and inventory verification in `pmiri.sealing`. | Implemented; current bundle is cryptographically verifiable but `INCOMPLETE` without external/review roles. |
| TD-009 | Local GC-C1 handoff uses a subprocess supervisor and Windows Job Object limits. | `pmiri.gc_c1_launcher.launch_pinned_runner` with shell-free argv, scrubbed environment, fresh case root, read-only inputs, CPU/memory/process limits, wall-time bound and teardown inspection. | Implemented as a local adapter; it deliberately requires an externally produced `VERIFIED` attestation and cannot self-authorize network/filesystem isolation. Replace or bind to the controlled-environment launcher before acceptance. |
| TD-010 | API and MCP read surfaces share one stateless semantic handler. | `pmiri.read_projection.ReadProjectionService` derives the binding server-side and emits an opaque continuation fingerprint; transport-supplied authorization references are ignored for authority. | Implemented and parity-tested locally; the authenticated path is now enforced through TD-014, while network serving and independent R-FC review remain outside this workspace. |
| TD-011 | Real provider/connector I/O uses an explicit HTTPS adapter and never follows redirects implicitly. | `pmiri.transports.HttpsJsonProviderTransport` and `HttpsConnectorTransport` require a matching `ALLOW` network decision, full validated connection binding, selected target, TLS identity match and explicit authorization; credentials enter only through `OpaqueCredential.inject`. The injected connection factory receives the decision’s prevalidated IP, the normalized hostname remains the TLS/SNI identity, the deployment-selected TLS context is passed to the default pinned connection, and `_PinnedHTTPSConnection.connect()` uses the selected IP for TCP while retaining the hostname for SNI. Gate-D independently denies TLS identity mismatch and final DNS-rebinding revalidation mismatch before selecting a target. Transport and boundary tests assert these invariants, including duplicate/hop redirect rejection and every response-limit/content-type rejection branch. The connector is also wired through the Gate-D runtime final fence with lifecycle validation. | Implemented and fake-connection/integration tested; real DNS/TLS/network execution remains disabled until controlled-environment authorization and deployment review exist. |
| TD-012 | Caller-facing read results use a leak-safe disclosure projection. | `pmiri.disclosure.project_query_result` collapses unauthorized reads and no-evidence results, removes counts/reasons, and preserves only server-derived lineage; `ReadProjectionService` exposes disclosed API/MCP methods. | Implemented and parity-tested locally; the local authentication/authorization boundary is implemented, while identity-provider deployment and independent R-FC review remain open. |
| TD-013 | Raw trace capture is opt-in, encrypted and short-lived with separated key domains. | `pmiri.privacy.EncryptedTraceStore` uses AES-256-GCM; `DpapiKeyProvider` protects independent per-domain keys with Windows user-scope DPAPI; reads require an allowed role and purge enforces TTL. | Implemented and locally tested; store-wide encryption, key rotation/escrow, multi-user identity, retention audit and deployment approval remain open. |
| TD-014 | Request authorization is derived at a trusted boundary and cannot be widened by caller fields. | `pmiri.request_auth` registers immutable authenticated principals, binds `AuthorizationSubjectChain` + `TrustZoneAttestation` + `PurposeBinding` into `RequestAuthorizationBinding`, checks exact project/purpose/operation scope and policy epoch, and applies process-safe replay/rate-limit fences. | Implemented and locally tested through the shared API/MCP read path; in-memory and durable local adapters exist, while deployed identity/revocation and distributed control-plane integration remain open. |
| TD-015 | Durable authorization state uses one transactional local control-plane database. | `pmiri.control_plane` provides SQLite/WAL adapters for principal registration/revocation, monotonic policy epochs, request replay IDs and fixed-window rate limits; payload fingerprints are re-derived on read. | Implemented and integration-tested across independent adapter instances; distributed deployment, identity-provider integration, database encryption and operational failover remain open. |
| TD-016 | SQLite content blobs use opt-in authenticated envelope encryption with explicit key versions. | `pmiri.storage_crypto.AesGcmBlobCipher` uses AES-256-GCM, binds domain/key-version/content fingerprint as AAD, accepts old key versions during rotation, integrates with `SQLiteStore`, and optionally calls `KeyEscrowAdapter` with only the new key fingerprint before activating a version. Encrypted backups preserve readability when the same cipher is supplied. | Implemented and locally tested; metadata/volume encryption, the real KMS/DPAPI escrow implementation, escrow persistence and production rollout remain deployment responsibilities. |
| TD-017 | External Gate-D emission must carry the server-derived request binding all the way to the final transport fence. | `GateDDecisionEngine.build_integrated_envelope` requires a valid `RequestAuthorizationBinding` for an allowed external envelope; `authorize_emission` checks the exact request/envelope binding and invokes a trusted authorization revalidator immediately before `EnforcedTransportRuntime` can call a provider or connector. | Implemented and regression-tested for missing, stale, revoked and substituted bindings; a real gateway/identity provider and independent review remain outside this workspace. |
| TD-018 | Gate-D invalidation and request authorization must share one durable policy epoch when deployed together. | `GateDDecisionEngine(policy_epoch_store=SQLitePolicyEpoch(...))` reads the current epoch and atomically bumps it through the SQLite control plane. | Implemented and locally tested; distributed epoch coordination, failover and operational deployment remain open. |
| TD-019 | R-FC replay is case-scoped and preflight/attestation-gated, with runner results separated from independent acceptance. | `pmiri.r_fc.run_r_fc_candidate` loads the documentation catalog, requires a per-case `READY_FOR_REPLAY` preflight record, digest-valid external attestation and exact fingerprints, dispatches pinned handlers through `run_controlled_case`, persists sealed outputs, validates evidence records and leaves status at `UNVERIFIED`/`FAIL` rather than `PASS`. | Implemented and tested for fail-closed missing-preflight behavior and one attested synthetic candidate case; all 34 cases and independent acceptance remain blocked until the controlled environment supplies attestations, handlers and review artifacts. |
| TD-020 | Every declared external read operation must pass the same projection and final-emission contract. | `pmiri.read_operations.ReadOperationService` exposes exactly the seven documented operations, binds the operation into the stateless cursor and typed result, and validates `ExternalReadEmissionFence` before returning API/MCP envelopes. | Implemented and locally tested for operation inventory, API/MCP parity, cursor substitution and fence tampering; independent Gate-C replay and production serving remain unclaimed. |
| TD-021 | Network authority uses one normative canonicalization profile and a concrete connection binding. | `pmiri.network` applies `D2-NETWORK-CANONICALIZATION-001`, uses the declared IDNA2008/UTS46 `idna` dependency for Unicode hostnames, rejects malformed/ambiguous targets, normalizes path/query/address values, and emits a fingerprinted binding containing the resolved set, selected target, proxy, TLS identity and revalidation epochs. `pmiri.gate_d` copies binding-derived fields into outbound decisions. | Implemented and tamper-tested locally; real resolver/TLS observations and controlled-environment network execution remain deployment-authorized work. |
| TD-022 | Capability, provider-policy and fetched-content lifecycle evidence must be typed and exact at runtime. | `pmiri.gate_d`, `pmiri.policy` and `pmiri.decisions` enforce closed value unions, exact field sets, scope/epoch/fingerprint checks, lifecycle admission/visibility fields and legal transition chains. | Implemented and locally tested; authority-supplied observations, production identity and independent Gate-D review remain external prerequisites. |
| TD-023 | Deployment readiness must be a read-only, fail-closed candidate report. | `pmiri.readiness` validates the closed deployment profile, authority/schema and local candidate artifacts, probes SQLite/control-plane health, confirms network default-deny, and lists external hard blockers. `init-control-plane` provides an explicit local bootstrap. | Implemented and tested; the report cannot authorize production, replace external attestation, supply identity/key escrow, or promote R-FC/D2 acceptance. |
| TD-024 | Local deployment and recovery must be proven as one reversible smoke chain. | `pmiri.deployment_smoke` runs synthetic fixture ingest, SQLite query, verified backup, no-overwrite restore, restored-query equality and local control-plane bootstrap in an isolated temporary root; `deployment-smoke` persists only a fingerprinted candidate report. | Implemented and tested; the smoke is local synthetic evidence and never authorizes external network/provider I/O or production deployment. |
| TD-025 | Release artifacts must be reproducible before deployment claims are considered. | `requirements.lock` pins runtime/build distributions; `scripts/verify_reproducibility.py` checks the pyproject/build contract and installed versions; setuptools discovery includes only `pmiri`; CI builds a wheel with locked build dependencies. | Implemented and locally verified; package-index trust, hash-locked mirror policy and remote CI execution remain deployment/supply-chain responsibilities. |
| TD-026 | Candidate readiness must never depend on a stale local seal. | `pmiri.deployment_smoke` refreshes `artifacts/sealed/s0-acceptance/artifact-manifest.json` immediately before the readiness probe and validates the resulting report. | Implemented and tested; the resulting seal remains local cryptographic integrity evidence, not independent review or production authorization. |
| TD-027 | The local API boundary must be authenticated and loopback-only until deployment authority exists. | `pmiri.http_api.LocalReadHTTPServer` requires `RequestAuthorizationService`, accepts a gateway-provided authentication reference header, bounds JSON body size, binds the operation to the URL and rejects non-loopback binds. | Implemented and tested; public network hosting, TLS termination, deployed IdP/gateway and real external transport remain open. |
| TD-028 | Local read outcomes must be auditable without creating a data-leak channel. | `pmiri.audit.ReadAuditEvent` and `JsonlAuditSink` persist only operation/outcome/status/fingerprints, validate every line and fsync each append; `LocalReadHTTPServer` refuses to emit a response if the configured sink cannot persist it. | Implemented and tested; centralized retention, independent audit administration and production log transport remain open. |
| TD-029 | Migration must be inspectable and reversible without mutating an existing target. | `SQLiteStore.migration_plan` computes source fingerprint/counts and target readiness without writes; `migrate_from_local_store` rejects an existing target; `backup_to` and `restore_from_backup` verify canonical fingerprints and enforce no-overwrite destinations. | Implemented and tested locally; production canary timing, rollback authority, backup retention and operational approval remain open. |
| TD-030 | Candidate operational metrics must remain low-sensitivity and concurrency-safe. | `pmiri.http_api.LocalReadMetrics` exposes loopback `/metrics` JSON with request, outcome and audit-failure counters guarded by a lock; it stores no request or identity fields. | Implemented and tested locally; production metrics transport, retention and independent monitoring remain deployment responsibilities. |
| TD-031 | Supply-chain inventory must be deterministic and derived from the exact lock. | `scripts/generate_sbom.py` emits and verifies SPDX 2.3 package/version/purl inventory for the 12 locked distributions plus PMIRI, enforces the canonical `SOURCE_DATE_EPOCH=946684800`, and the candidate audit checks the tracked SBOM directly; it intentionally marks distribution hashes `NOASSERTION` until a trusted mirror provides them. | Implemented and tested locally; mirror trust, hash-pinned acquisition and external CI provenance remain deployment responsibilities. |
| TD-035 | Hash-pinned acquisition must be verified at the deployment boundary without inventing mirror evidence locally. | `scripts/verify_supply_chain.py` accepts a deployment-supplied `name==version --hash=sha256:...` lock, requires the exact repository inventory, and optionally verifies every offline wheel/source archive against a supplied SHA-256. It never downloads from a public index. | Implemented and tested locally; the actual trusted mirror, hash lock and provenance remain external deployment inputs. |
| TD-036 | Local key and authorization state must preserve invariants under concurrent workers. | `DpapiKeyProvider` serializes per-domain key-record creation with a process-local path mutex plus a cross-process file lock; `EncryptedTraceStore` accepts only generated trace identifiers; concurrent SQLite tests verify single-consumer replay, exact rate-limit ceilings and unique monotonic epoch bumps. | Implemented and tested locally, including repeated Windows DPAPI first-key race stress; production KMS/escrow, distributed coordination and deployment ACLs remain external. |
| TD-037 | Case evidence seals must not depend on local analysis/build caches, live runtime state or derived transfer bundles. | `pmiri.sealing._is_non_evidence` excludes Graphify/codebase-memory output, build metadata, local runtime stores, the live `artifacts/read-audit.jsonl` sink and `artifacts/handoff*` while retaining candidate evidence; regression tests verify the scope. | Implemented and tested locally; external reviewer evidence and final deployment attestation remain absent. |
| TD-038 | Case sealing must never follow a symlink to content outside the candidate root. | `seal_directory` and `verify_seal` skip symlink entries before hashing or inventory comparison; a regression test creates an outside-root target and confirms it is not sealed. | Implemented and tested locally; clean-room filesystem observation and external review remain absent. |
| TD-039 | R-FC handler dispatch must be bound to an explicit immutable module/source manifest. | `pmiri.r_fc.create_handler_manifest` and `load_handler_manifest` bind the selected `HANDLERS` symbols to one module, source path and SHA-256; `rfc-run` requires the standalone `artifacts/r-fc-handler-manifest.json`, while readiness checks its 34-case catalog/source binding before replay. | Implemented and tested locally; the actual external attestation, authorization and independent review remain deployment inputs. |
| TD-040 | GC-C1 preflight must verify the complete pinned runner package, not merely any present member hashes. | `pmiri.preflight._verify_runner_package` enforces exact manifest identity, three-file inventory, canonical member paths, source/manifest SHA-256 values, self-hash marker and deny-by-default package boundary flags. | Implemented and tested locally; external clean-room execution and independent acceptance remain absent. |
| TD-041 | Deployment readiness may consume external claims only through a separately trusted, signed evidence bundle. | `pmiri.deployment_evidence.verify_external_evidence` verifies Ed25519 signatures, trusted key IDs, profile/authority fingerprints, all EXT-01..EXT-06 observations and independent review separation; `readiness` keeps the default no-evidence path blocked. | Implemented and tested locally with tamper rejection; the authorized deployment key and real observations remain external inputs. |
| TD-042 | Local R-FC coverage must exercise PMIRI boundaries without being confused with attested acceptance. | `pmiri.r_fc_handlers` and `rfc-local` execute all 34 declared positive/adversarial cases against fresh synthetic state and emit a self-fingerprinted `LOCAL_SYNTHETIC_ONLY` report; `r_fc_pass` remains `NONE` and the attested runner retains its external gates. | Implemented and tested with 34/34 oracle matches; clean-room attestation, external observations and independent review remain absent. |
| TD-032 | Local serving must be assembled from fail-closed adapters and never accept a remote bind. | `pmiri.server.build_local_read_server` wires an existing SQLite content store, SQLite control-plane adapters, `ReadOperationService`, redacted audit and `LocalReadHTTPServer`; `serve-local` exposes only `127.0.0.1` and emits the active profile ID/fingerprint plus effective storage/control-plane paths; `tests/test_cli_serve_local.py` verifies the real subprocess lifecycle, health/metrics, generic auth rejection and audit redaction. | Implemented and tested locally; deployed identity, public hosting, TLS termination and distributed failover remain open. |
| TD-033 | Clean-room handoff must be materialized, fingerprinted and non-overwriting while preserving the external review boundary. | `pmiri.handoff.create_handoff_bundle` copies synthetic fixtures, pinned runner/authority inputs, lock/SBOM and candidate evidence into a caller-selected immutable release directory; `scripts/create_handoff.ps1` selects the next unused `handoff-release-vN`; `verify_handoff(..., project_root=...)` checks the exact manifest, payload inventory/fingerprints and current source inventory/fingerprints. The candidate-root seal and reduced handoff transfer manifest are documented as separate scopes. | Implemented and tested locally; the bundle is ready for external review but cannot create clean-room attestation or independent acceptance. |
| TD-043 | External review must receive one bounded, self-fingerprinted inventory without confusing local candidate evidence with acceptance. | `pmiri.review_package.build_review_package` consolidates the local report fingerprints, exact PF-01..PF-16 preflight contract, D2/R-FC/recovery counts, a local/external/final closure matrix and EXT-01..EXT-06 actions; `validate_review_package(..., project_root=...)` re-derives that inventory from the current reports so a resigned package cannot drift from its source evidence; `review-package` writes it for handoff while preserving `NOT_PERFORMED`, `NONE` and independent-review non-claims. | Implemented and tested locally; external observations, review and promotion remain outside this workspace. |
| TD-045 | Release wheel bytes must be reproducible across independent builds. | CI fixes `SOURCE_DATE_EPOCH`, builds the wheel twice in separate directories, compares SHA-256, installs the selected wheel into an isolated target and persists that target through later steps; the first import and runtime CLI checks run outside the checkout with explicit workspace/output paths, while the test runner preserves repository-relative fixtures but puts the installed wheel first. The runbook carries the same epoch into local release builds. | Implemented and verified locally with two independent builds, isolated-target tests and installed-runtime CLI chain; trusted CI provenance and deployment mirror approval remain external. |
| TD-044 | Deployment-owned identity, revocation and coordination adapters must be injectable without silently creating a second local authority. | `pmiri.server.ServerAuthorizationAdapters` defines the injected registry/replay/rate-limit/policy-epoch port set through public `Protocol` contracts; `build_local_read_server` validates the complete method surface and non-negative epoch, maps epoch-store outages to a configuration failure, uses supplied objects directly, and validates an optional `BlobCipher` before assembly. `tests/test_server.py` now exercises an injected principal through the real HTTP read path and verifies that adapter revocation changes the response to an existence-safe empty projection. The default remains the initialized local SQLite adapter set. | Implemented and contract-tested locally; deployed IdP/revocation, distributed coordination, key escrow and public network authority remain external deployment inputs. |
| TD-034 | Read-server deployment settings must be part of the closed readiness profile. | `deployment-profile.example.json` and `pmiri.readiness.validate_profile` require `HTTP_LOOPBACK`, `127.0.0.1`, bounded port/request size and a project-local audit path; `serve-local --profile` consumes API plus profile-derived SQLite storage, control-plane and audit paths when overrides are omitted, while retaining the hard loopback constructor; the release audit independently loads the in-project profile and rejects canonical profile/readiness drift. | Implemented and tested locally; public hosting, TLS termination and deployed identity remain external. |
| TD-046 | Deployment readiness must not be mistaken for final acceptance. | `pmiri.final_acceptance` and `final-acceptance` validate FA-01 readiness plus the exact signed FA-02 D2 acceptance, FA-03 R-FC 17/17 PASS, FA-04 migration/restore/failover, FA-05 independent review and FA-06 operations approval assertions. The gate binds evidence to the active profile, authority and readiness report, requires verified evidence metadata for `READY`, and fails closed when evidence is absent, partial, invalid or self-reviewed. | Implemented and tested locally, including positive and tampered CLI evidence paths; controlled execution, independent review, operational approval and signed deployment evidence remain external. |

No decision in this file authorizes production ingestion, migration, external
provider access, connector credentials, network access, R-FC PASS, or D2
acceptance.
